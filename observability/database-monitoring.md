# 数据库监控：五层监控指标

从机器到集群逐层检查：**基础设施 → 数据库服务 → 数据库性能 → 数据与存储 → 高可用与复制**。

数据库专项：[MongoDB](mongodb/README.md) · [PostgreSQL](postgresql/README.md) · [Oracle](oracle/README.md)。

> 以下阈值是告警示例，不是所有环境通用的标准。应结合业务 SLO、RPO、历史基线、磁盘容量和峰值负载调整。资源类指标可要求持续 5 分钟再告警；服务不可用等故障应及时告警。告警最好区分警告、严重和恢复，并避免短暂抖动造成误报。

## 基础设施层（OS / Network）

**核心问题：机器、磁盘和网络是否健康？**

### CPU 使用率

CPU 是否长期繁忙。

**告警参考：**> 80% 持续 5 分钟警告；> 90% 严重告警。

**排查方式：**`mpstat -P ALL 1`。查看各 CPU 的 `%usr`、`%sys`、`%iowait`、`%idle`。

### Load Average

运行及不可中断任务的负载，结合 CPU 核数、IO 等待判断。

**告警参考：**持续明显高于 CPU 核数且偏离基线时排查。

**排查方式：**`uptime`；`nproc`。对照 CPU 核数，并结合 IO 等待，不把 load 当作 CPU 使用率。

### 可用内存

关注可用内存，而不只看空闲内存；Linux 文件缓存可回收。

**告警参考：**可用内存 < 10% 持续 5 分钟；结合 OOM 事件判断。

**排查方式：**`free -h`。查看 `available`，而不是只看 `free`。

### Swap

已使用量、换入换出速率。

**告警参考：**持续发生换入换出，或使用量持续增长时告警。

**排查方式：**`free -h`；`vmstat 1`。查看 Swap 用量及 `si`、`so` 是否持续非零。

### 磁盘容量与 inode

数据、日志、备份所在文件系统的剩余空间和 inode。

**告警参考：**使用率 > 85% 警告，> 95% 严重告警；同时预测耗尽时间。

**排查方式：**`df -h`；`df -i`。分别查看数据、日志和备份文件系统。

### 磁盘 IO

读写 IOPS、吞吐量、读写延迟和 IO 等待。

**告警参考：**延迟持续明显高于基线或超过存储服务目标；IOPS 结合设备能力判断。

**排查方式：**`iostat -x 1`。看读写次数、吞吐量、`await`；字段随版本变化。

### 网络

带宽、丢包、错误包、TCP 重传、节点间 RTT。

**告警参考：**丢包、重传或 RTT 持续高于基线；带宽接近链路上限时告警。

**排查方式：**可以按照链路层、网络层和传输层逐步缩小范围。工具展示的是系统统计信息，某些统计可能跨越多个协议层，需结合实际路径判断。

#### 链路层：网卡和链路

先检查网卡是否正常、链路速率是否符合预期，以及流量、错误和丢包是否持续增长。

| 命令 | 用途 |
|---|---|
| `ip -s link` | 查看各网卡收发字节数、错误和丢包等累计计数；间隔采样可判断增长速度。 |
| `sar -n DEV,EDEV 1` | 每秒查看网卡流量和错误统计。`DEV` 是网络设备流量统计，`EDEV` 是网络设备错误统计，可关注错误和丢包等字段；需要 `sysstat`。 |
| `ifstat 1` | 按网卡查看实时收发速率；需要单独安装，输出单位以命令显示为准。 |
| `ethtool <网卡名>`；`ethtool -S <网卡名>` | 查看链路速率、状态和网卡驱动统计；统计字段取决于网卡和驱动。 |

#### 网络层：地址、路由和节点可达性

确认节点使用了预期的 IP 地址和路由，再检查到目标节点的往返时间和丢包。数据库跨网段或跨机房访问时，应从实际客户端所在的网络进行探测。

| 命令 | 用途 |
|---|---|
| `ip addr show` | 查看网卡 IP 地址及状态。 |
| `ip route get <节点地址>` | 查看系统访问目标地址时选择的路由、出口和源地址。 |
| `ping -c 10 <节点地址>` | 查看 ICMP 往返时间和丢包；ICMP 受限时应结合实际业务端口探测。 |
| `sar -n IP,EIP 1` | 每秒查看 IPv4 数据报及错误统计。`IP` 包括接收、交付、转发和分片等统计；`EIP` 包括报头错误、丢弃及路由或重组失败等统计。 |
| `sar -n ICMP,EICMP 1` | 每秒查看 ICMPv4 报文及错误报文统计，如 Echo 和目标不可达等；这些是本机协议统计，不能直接当作某条链路的丢包率。 |
| `sar -n IP6,EIP6,ICMP6,EICMP6 1` | 查看 IPv6 和 ICMPv6 的流量及错误统计；字段和可用性取决于 sysstat 版本及系统。 |
| `nstat -az \| grep -E '^(Ip\|Icmp)'` | 筛选 IP 和 ICMP 相关累计统计（包括扩展及 IPv6 字段）；对比多次采样判断变化。 |

例如，`sar -n IP,EIP 1 5` 每秒采样一次，共输出五次。`irec/s` 是每秒收到的 IPv4 数据报数，`idel/s` 是每秒成功交付给上层协议的数据报数；`ihdrerr/s` 是每秒因 IP 报头错误而丢弃的数据报数，`onort/s` 是每秒因无路由而丢弃的输出数据报数。应结合趋势、路由和业务访问路径分析，而不是把这些主机级计数直接当作某个数据库连接的指标。

`sar` 实时采样和历史文件查询的可用数据可能不同；历史采集需要启用对应的 SNMP 或 IPv6 统计。字段及选项见 [sysstat 的 sar 手册](https://github.com/sysstat/sysstat/blob/master/man/sar.in)。

#### 传输层：TCP 连接和重传

网络可达后，继续检查数据库端口是否监听、连接状态是否异常，以及 TCP 重传和延迟是否增加。

| 命令 | 用途 |
|---|---|
| `sar -n TCP,ETCP 1` | 每秒查看 TCP 连接活动和错误统计。`TCP` 关注连接活动，`ETCP` 是 TCP 错误统计，可关注重传、连接失败和重置等字段。 |
| `ss -s` | 汇总 socket 和 TCP 连接状态，快速观察连接数量是否异常。 |
| `ss -lntp` | 查看监听中的 TCP 端口和对应进程；查看进程信息可能需要更高权限。 |
| `ss -nto` | 查看 TCP 连接及计时器；加上 `-i` 可查看支持的 TCP 内部信息，如 RTT 和重传。 |
| `nstat -az \| grep -E '^Tcp'` | 筛选 TCP 和 TCP 扩展统计，包括重传；这些是累计计数，对比多次采样判断变化。 |
| `nstat -az \| grep -E '^Udp'` | 筛选 UDP 及相关扩展、IPv6 统计；对比累计计数的采样差值。 |
| `nc -z -w 3 <节点地址> <端口>` | 测试 TCP 端口是否能够建立连接；端口可达不代表数据库认证或查询成功。 |

`sar` 的具体字段随 `sysstat` 版本和系统而异。如果使用 `ipstat`，其功能和输出取决于安装的软件包；`ip -s link`、`ifstat` 和 `sar` 可用于查看网卡计数或速率。累计计数器可能在重启或接口重置后归零，分析时应关注采样区间内的变化。

### VIP

VIP 是否位于预期的活动节点，客户端是否能通过 VIP 访问服务。

**告警参考：**VIP 不在预期节点或从业务侧探测不可达时及时告警。

**排查方式：**`ip addr show`；`nc -z -w 3 <VIP> <端口>`。分别检查地址归属和业务网络到端口的连通性；端口通不代表数据库查询成功。

常用排查命令：`top`、`free -h`、`df -h`、`df -i`、`iostat -x 1`、`ip addr`。Linux 的 `available` 内存通常比单独的 `free` 更有参考价值；`iostat` 可重点观察 `await` 等指标。

Linux 示例中的 `<...>` 需要替换为实际值；部分命令需要安装 `sysstat`、`iproute2` 或 `netcat`。

主机指标应结合时间趋势和业务表现分析。例如 CPU 升高时，先区分用户态、内核态和 IO 等待，再对照数据库请求量；负载升高但 CPU 尚有空闲时，应检查是否有任务等待磁盘。磁盘除了看当前使用率，还要根据增长速度预估剩余时间。网络指标应同时观察客户端到服务端和集群节点之间的路径。

## 数据库服务层（Availability / Connections）

**核心问题：数据库是否能从业务入口正常连接和执行请求？**

### 进程与端口

数据库进程是否存活、服务端口是否监听。

**告警参考：**进程退出或端口不可用时及时告警。

### 端到端可用性

从业务网络经实际入口连接、认证并执行轻量查询；MongoDB 可使用 `ping`。

**告警参考：**连续探测失败或探测超时及时告警；探测账号权限应最小化。

**排查方式：**使用各数据库专项中的连接测试及会话查询。从业务网络和实际服务入口探测。

### 当前连接数

已建立连接数，以及与可用连接上限的比例。

**告警参考：**连接使用率 > 80% 警告，> 90% 严重告警。

### 活跃和等待连接

正在执行、等待锁或其他资源的会话数量。

**告警参考：**持续高于正常峰值或等待会话持续增加时排查。

### 连接建立失败

连接拒绝、认证失败、连接超时。

**告警参考：**失败率持续高于基线或超过业务目标时告警。

连接使用率应以**实际可供业务使用的连接额度**为分母，并考虑管理员预留连接、连接池和实例限制。连接数高不一定代表数据库忙，需要同时看活跃会话和等待情况。

示例：PostgreSQL 查询 `pg_stat_activity`；MySQL 查看 `Threads_connected` 和 `Threads_running`；MongoDB 查看 `db.serverStatus().connections`。

可用性探测需要覆盖解析地址、建立连接、身份认证和执行查询的完整路径。进程存在或端口打开只能证明部分环节正常，不能证明应用可以读写。探测失败时，可依次检查网络、认证、连接池和数据库日志；同时保留管理连接，便于连接耗尽时排障。

## 数据库性能层（Performance）

**核心问题：数据库处理请求是否足够快、是否出现阻塞或异常负载？**

### QPS / TPS

每秒查询量、每秒事务量及其变化趋势。

**告警参考：**同时段对比历史基线；突增、突降或吞吐量下降且延迟上升时告警。

**排查方式：**使用各数据库专项中的计数器、日志和等待查询。累计值按采样窗口计算增量，注明统计口径。

### 响应时间

平均值、P95、P99，以及时间窗口内最慢请求。

**告警参考：**P95/P99 持续超过业务 SLO；最慢请求超过超时或慢查询阈值时排查。

**排查方式：**查询应用或驱动的请求耗时直方图与日志。需要预先埋点；数据库累计平均耗时不能还原精确分位数或最慢请求。

### 慢 SQL

慢查询数量、占比、耗时和 Top SQL。

**告警参考：**慢查询数量或占比持续高于基线；重点关注影响核心业务的 SQL。

### 锁等待

等待数量、等待时长、阻塞会话。

**告警参考：**等待时间超过业务容忍值或等待会话持续增长时告警。

### 死锁

单位时间内死锁次数及涉及的事务。

**告警参考：**发现死锁时记录并告警；重复发生时提高严重级别。

### 错误与超时

查询失败率、事务回滚、请求超时。

**告警参考：**错误率或超时率超过业务目标或持续偏离基线。

QPS/TPS 通常由累计计数器在采样窗口内的**增量 / 时间**得到，注意计数器重置。不同数据库和监控工具对“查询”和“事务”的统计口径不同；应明确是否包含提交、回滚、内部操作和失败请求。P95/P99 应基于请求耗时分布计算，不能用平均值代替；最慢请求也要注明统计窗口。

例如，应用已向 Prometheus 暴露 `db_request_duration_seconds_bucket` 直方图时，可按五分钟窗口计算 P95：

```promql
histogram_quantile(0.95, sum by (le) (rate(db_request_duration_seconds_bucket[5m])))
```

将 `0.95` 改为 `0.99` 可计算 P99；指标名只是示例，实际需替换为应用暴露的指标。直方图估算分位数，不提供精确的窗口内最大值；最慢请求应从对应窗口的请求日志或追踪记录查找。

性能排查先确认影响范围和发生时间，再对照吞吐量、延迟、错误率和资源使用率。吞吐量下降且延迟上升时，进一步查看慢查询、执行计划及锁等待，区分请求增加、单条查询变慢和资源争用。处理锁问题时应找到阻塞源及其事务状态，评估业务影响后再采取措施。

## 数据与存储层（Data / Storage）

**核心问题：表、索引、缓存和日志是否正在成为容量或性能瓶颈？**

### 表和数据文件

表大小、数据文件或表空间使用率、增长速度。

**告警参考：**可用空间低于容量规划要求；按近期增长率预测短期内耗尽时告警。

**排查方式：**使用各数据库专项中的对象、日志及集群查询。分别检查各实例和副本；事件需结合数据库或集群日志。

### 索引

索引大小、使用情况、膨胀趋势。

**告警参考：**大索引长期未使用或增长异常时排查；删除前确认约束和业务用途。

### 缓存命中率

数据库缓存命中与磁盘读取的比例。

**告警参考：**持续明显低于自身基线且磁盘读取或延迟上升时排查；不单独以 99% 判断健康。

### 事务日志

PostgreSQL WAL、MySQL Binlog/Redo 的占用、增长、保留和清理情况。

**告警参考：**日志所在文件系统 > 85%；日志增长异常或预计耗尽空间时告警。

### 数据清理

PostgreSQL dead tuples、VACUUM 进度；其他数据库关注各自清理或后台任务。

**告警参考：**垃圾数据或清理积压持续增长并影响空间、性能时排查。

缓存命中率需结合工作负载、统计时间窗口和 OS 缓存判断。WAL/Binlog 持续增长可能与复制、归档或保留策略有关；Redo 通常有固定容量或循环使用机制，需结合数据库版本及配置判断，不能一概视为复制故障。

容量监控需要同时覆盖数据库对象和底层文件系统：对象增长正常也可能因为日志、备份或其他文件占满磁盘。观察索引和缓存时，应结合实际查询、物理读取和延迟。清理日志或删除索引前，应确认复制、恢复、归档及业务依赖。

## 集群层（HA / Replication）

**核心问题：集群是否可用，副本是否及时同步，故障切换是否正常？**

### 节点与角色

主节点、备节点是否在线，角色是否符合预期。

**告警参考：**主节点不可用、节点异常离线或角色异常时及时告警。

### Quorum / 仲裁

采用仲裁机制的集群是否仍有法定多数。

**告警参考：**失去 Quorum 立即告警；可容忍故障余量不足时提前警告。

### 复制状态

复制连接、发送和接收进程、错误信息。

**告警参考：**复制中断、报错或副本长期未更新时及时告警。

### 复制延迟

发送、接收、写入、持久化或回放进度，以及时间或字节积压。

**告警参考：**延迟超过业务允许值时告警；参考 RPO 设置严重级别，并结合复制状态判断数据丢失风险。

### 节点间网络

集群节点及跨机房 RTT、丢包、吞吐量。

**告警参考：**RTT 或丢包持续高于基线并影响复制、心跳时告警。

**排查方式：**`ping -c 10 <节点地址>`。查看往返时间和丢包；ICMP 被禁用时需使用其他网络探测。

### 故障切换

切换是否成功、耗时、切换频率。

**告警参考：**切换失败立即告警；耗时超过 RTO 或短时间反复切换时告警。

复制延迟指标的含义和可用性因数据库而异；时间延迟、字节积压不可直接互换，**缺失或无法计算的延迟不能当作零**。例如 PostgreSQL 可查看 `pg_stat_replication` 的写入、持久化和回放进度；MySQL 可查看副本状态；MongoDB 可查看 `rs.status()` 和副本集复制状态。

集群监控既要看节点是否在线，也要验证客户端能否通过预期入口访问正确角色。副本延迟应结合复制连接、积压和业务写入情况判断；低写入时某些时间指标可能没有更新。定期演练切换与恢复，并记录实际恢复时间，才能检验高可用方案是否达到目标。

## 面试总结

| 层次 | 一句话 | 核心指标 |
|---|---|---|
| 基础设施 | 机器和网络健不健康 | CPU、内存、磁盘、IO、网络、VIP |
| 服务 | 数据库能不能连上 | 进程、端口、探测、连接数 |
| 性能 | 请求处理得快不快 | QPS、TPS、P95/P99、慢 SQL、锁等待 |
| 数据与存储 | 数据、索引和日志会不会成为瓶颈 | 容量、增长率、索引、缓存、WAL/Binlog/Redo |
| 集群 | 高可用和数据同步是否正常 | 节点、Quorum、复制延迟、RTT、切换 |
